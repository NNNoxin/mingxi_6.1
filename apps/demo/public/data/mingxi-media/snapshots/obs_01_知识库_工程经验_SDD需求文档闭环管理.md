# SDD 需求文档闭环管理

> **核心思想**：代码报错 → 需求文档修正 → 长期记忆沉淀，形成 SDD 闭环

---

## 一、两个核心工作流

### Workflow A：代码报错 → 长期记忆

**场景**：调试时遇到 bug，修好后随手记录，沉淀为可复用的工程经验。

**流程**：
```
代码报错
   ↓
定位原因（参数名错误 / 逻辑矛盾 / 依赖版本冲突...）
   ↓
修复
   ↓
记录：错误现象 + 根因 + 修复方法 + 教训
   ↓
写入工程经验库（本 vault）→ 长期记忆
```

**价值**：同类错误第二次遇到，直接查记录，不用再踩一遍。

---

### Workflow B：代码报错 → 反向修正需求文档（SDD 闭环）

**场景**：按需求文档实现时出现报错，定位后发现是**需求文档本身存在矛盾**。

**核心原则**：
> **实现通过测试 → 实现是对的 → 文档向实现对齐**  
> 不是"改代码去符合文档"，而是"改文档去符合已验证的代码"

**流程**：
```
代码报错
   ↓
判断根因：
  ├── 实现有 bug？→ 修代码
  └── 需求文档与实现矛盾？→ 修文档（Workflow B）
          ↓
     最小修改原则：
       - 只消除矛盾，不扩展功能
       - 不改变原有功能语义
       - 改动范围最小化
          ↓
     记录变更到 CHANGELOG.md：
       说明"为什么改"（不只是"改了什么"）
```

---

## 二、真实案例：Makefile 参数名矛盾

**问题**：
- Makefile 写的是 `--n 5` 和 `--output-dir`
- CLI 实际参数是 `--limit` 和 `--output`

**根因判断**：
- 代码已通过 239 个测试 → 实现是对的
- 问题出在需求文档/Makefile 没有跟随代码更新

**处理方式**：
- ✅ 修改 Makefile（文档侧）：`--n 5` → `--limit 5`，`--output-dir` → `--output`
- ✅ 在 CHANGELOG 记录：参数名与实现不一致，向实现对齐
- ❌ 不修改已通过测试的代码逻辑

**教训**：
> 需求文档是**活的**。实现演化时，文档必须跟上；如果没跟上，以代码为准。

## 三、判断"改文档"还是"改代码"的决策树

```
出现矛盾（文档 vs 代码）
   ↓
代码有测试覆盖且测试通过？
  ├── 是 → 文档向代码对齐（改文档）
  └── 否 → 判断功能语义
              ├── 文档描述的功能更合理 → 改代码，补测试
              └── 代码行为更合理 → 改文档，注明原因
```

**特殊情况**：如果改动会影响已有功能语义，**必须**：
1. 先在 CHANGELOG 说明影响范围
2. 更新相关测试用例
3. 走 code review（如果是团队项目）

## 四、CHANGELOG 写法规范

**好的 CHANGELOG 条目**（说明"为什么"）：
```markdown
## [日期] fix(docs): 对齐 CLI 参数名与实现

- `--n` → `--limit`：代码实现已使用 --limit，文档未同步
- `--output-dir` → `--output`：同上

原因：代码已通过 239 tests，实现为准，消除文档矛盾。
功能语义不变。
```

**差的 CHANGELOG 条目**（只说"改了什么"）：
```markdown
## [日期] 更新文档
- 修改了参数名
```

## 五、关于"代码报错记录为长期记忆"的可行性

**现在就能做**，不需要额外工具：

| 方式 | 做法 |
|------|------|
| **即时记录** | 调试完后，把错误现象+根因+修复写入本 vault |
| **批量整理** | 一个任务结束后，回顾本次所有报错，批量写入 |
| **按项目分类** | 存入 `02.科研/ARIS-mNGS/实验记录/` 或本目录 |
| **跨项目通用经验** | 存入 `01.知识库/工程经验/`（本目录）|

**建议格式**：

```markdown
### [错误类型] 简短描述

**现象**：
**根因**：
**修复**：
**预防**：（下次如何避免）
```

## 六、适用场景总结

| 场景 | 方案 |
|------|------|
| 代码报错，是 bug | 修代码 + 补测试 + 记录到工程经验库 |
| 代码报错，是文档矛盾 | 最小修改文档 + 记 CHANGELOG + 记工程经验库 |
| 需求变更导致旧代码失效 | 修代码 + 更新文档 + 记 CHANGELOG |
| 调试中发现文档模糊 | 澄清文档 + 不改代码 |
